# Отчет по практическим занятиям 7–11

## Практическое занятие 7: Базовые методы аутентификации

Создана базовая структура сервера с аутентификацией на основе паролей, хешированных с помощью bcrypt.

### Реализовано
- Хеширование паролей с солью (bcrypt, 10 раундов).
- Маршруты:
  - `POST /api/auth/register` — регистрация пользователя (email, имя, фамилия, пароль)
  - `POST /api/auth/login` — вход в систему (проверка пароля)
- CRUD для товаров с хранением в памяти:
  - `GET /api/products` — список товаров
  - `GET /api/products/:id` — товар по ID
  - `POST /api/products` — создание
  - `PUT /api/products/:id` — обновление
  - `DELETE /api/products/:id` — удаление

## Практическое занятие 8: JWT-токены

Система теперь использует JWT для идентификации пользователя. Защищённые маршруты доступны только при наличии валидного токена.

### Реализовано
- Генерация **access-токена** при успешном входе.
- Создание **authMiddleware** для проверки JWT в заголовке `Authorization: Bearer <token>`.
- Добавление защищённого маршрута:
  - `GET /api/auth/me` — возвращает информацию о текущем пользователе (требует токен).

## Практическое занятие 9: Refresh-токены

Реализована полная схема работы с access и refresh токенами. При истечении access-токена клиент может получить новый без повторного ввода пароля.

### Реализовано
- Разделение секретов и времени жизни:
  - `ACCESS_SECRET`, `ACCESS_EXPIRES_IN = "15m"`
  - `REFRESH_SECRET`, `REFRESH_EXPIRES_IN = "7d"`
- Добавление маршрута:
  - `POST /api/auth/refresh` — принимает refresh-токен, выдаёт новую пару токенов.

## Практическое занятие 10: Хранение токенов на фронтенде

Реализовано хранение токенов на фронтенде.

### Реализовано
- Настройка **axios** с перехватчиками:
  - Добавление `Authorization: Bearer <accessToken>` в каждый запрос.
  - Автоматическое обновление access-токена при получении ошибки 401.
- Реализованы страницы:
  - Вход / Регистрация
  - Список товаров
  - Создание / редактирование товара
  - Просмотр деталей товара
- Хранение токенов в **localStorage**.

## Практическое занятие 11: Управление доступом на основе ролей

Реализована полноценная система контроля доступа. Каждый маршрут защищён в соответствии с правами роли.

### Реализовано
- Добавлено поле `role` в модель пользователя (значения: `user`, `seller`, `admin`).
- Создан **roleMiddleware**, проверяющий роль пользователя из JWT.
- Разграничение доступа
- На фронтенде реализовано отображение интерфейса в зависимости от роли.
